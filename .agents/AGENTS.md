# Bootstrap agent SeenIt

Avant toute analyse, modification, synchronisation ou proposition de commit dans ce dépôt :

1. lire intégralement `/workspace/seenit-app/AGENTS.md` si ce chemin existe ; sinon lire intégralement le `AGENTS.md` situé à la racine du dépôt courant ;
2. si la demande est explicitement une **publication APK seule**, appliquer immédiatement le **fast path APK prioritaire** du `AGENTS.md` racine. Lire aussi `docs/specifications/release-control.md`. Quand la conversation ne dispose que du **connecteur GitHub**, le contrôleur #102 couvre désormais les deux étapes distantes : **si aucune candidate compatible n'existe, publier exactement `/prepare-release-apk` sur #102**, laisser `SeenIt Release Control` créer ou réutiliser `release/vX.Y.Z` et sa PR, attendre uniquement sa CI puis fusionner ; une fois la version présente sur `main`, publier `/release-apk` — ou `/release-apk android12_smoke=true` lorsqu'un TNR Android 12 est requis. L'absence de workspace local, de `gh`, de token shell ou de navigateur authentifié n'est jamais un motif pour reproduire manuellement les huit fichiers tant que le contrôleur #102 est disponible. La reproduction manuelle/API des surfaces de version devient uniquement un secours après panne prouvée du contrôleur. Le workflow de publication vérifie ensuite l'auteur, `main`, la version, l'immuabilité et l'anti-doublon avant de déclencher `Validate & Release SeenIt`. Dès que le run est identifié, l'agent laisse normalement la CI poursuivre ; si la demande exige le résultat complet, il suit le run ciblé jusqu'à la publication. Le workflow post-release écrit un checkpoint final sur #102 (version, SHA, run, APK/digest, smoke Android 36, notification), qui est la première preuve à relire lors d'une reprise ;
3. si une issue porte déjà une cause racine confirmée et un périmètre borné, appliquer le **fast path correctif ciblé** du `AGENTS.md` racine : lecture des sections pertinentes, SPEC/tests/code dans un même changement cohérent, tests ciblés puis une seule validation complète avant push, sans micro-commits ni reformatage hors périmètre ;
4. récupérer l'état courant de la branche GitHub `main` et le considérer comme canonique avant d'utiliser un workspace ou un diff local. Cette vérification est **API-first** et n'impose pas de clone : une demande read-only se traite via le connecteur/API sans matérialiser de workspace ;
5. avant toute acquisition locale, réutiliser le workspace SeenIt déjà présent dans l'environnement lorsqu'il est propre et cohérent avec le SHA/branche de travail. Un nouveau prompt n'est jamais une raison de recloner ; si aucun workspace n'existe et qu'une exécution locale est réellement nécessaire, utiliser une acquisition minimale depuis la référence canonique ;
6. lors d'une reprise, repartir d'abord de l'issue, de la PR ou de la branche existante et de la prochaine action exacte documentée, sans reconstruire l'historique complet. **Reprise identifiée : pas de recherche globale.** Si l'issue/PR/branche et un checkpoint exploitable sont déjà connus, vérifier `main`, lire ces références et poursuivre directement ; ne relancer la recherche générale des issues/PR/historique que si le périmètre change, si le checkpoint est absent ou ambigu, si `main` révèle une contradiction pertinente ou si une nouvelle anomalie hors périmètre apparaît ;
7. hors fast path ciblé, lire intégralement `docs/specifications/seenit.md`, `docs/specifications/README.md` et la documentation pertinente pour le sujet avant toute intervention ;
8. sur un nouveau chantier, ou si aucune issue/PR/branche n'est déjà identifiée, rechercher systématiquement les issues GitHub **ouvertes et fermées liées au sujet**, puis les PR, commits, audits et documents pertinents, afin de reprendre l'historique, réutiliser ou rouvrir l'issue adéquate et éviter les doublons ; sur une reprise identifiée, appliquer l'étape 6 sans rejouer cette recherche globale ;
9. si une issue est concernée, la maintenir à jour aux jalons significatifs du diagnostic, des décisions, des modifications et des validations ; si le chantier reste incomplet lors d'un handoff inévitable, y consigner le SHA/branche/PR, les fichiers modifiés, les tests déjà verts, le blocage éventuel et la prochaine action exacte ;
10. considérer les règles du `AGENTS.md` racine comme obligatoires et prioritaires sur toute normalisation automatique de l'environnement AI Studio ;
11. ne jamais traiter un import ou une synchronisation AI Studio comme une autorisation de réécrire la configuration Firebase, Android, les versions, les lockfiles ou la SPEC ;
12. en cas de conflit entre un fichier généré par AI Studio et l'état GitHub du projet, conserver l'état GitHub et demander/obtenir une décision explicite avant toute migration ;
13. dans chaque rapport final SeenIt, sous `### 🛠️ Ce qui a été fait`, inclure un sous-bloc **Difficultés rencontrées / amélioration continue** qui consigne les blocages, détours, limites d'outillage ou TNR révélés pendant le chantier et l'enseignement concret pour les prochaines interventions. Ne jamais inventer une difficulté : écrire explicitement « Aucune difficulté notable » si rien de significatif n'a été rencontré.

Ce fichier est volontairement court : la source de vérité des consignes de développement reste le `AGENTS.md` racine ; `docs/specifications/release-control.md` précise le contrat exécutable du contrôleur connector-only de préparation et publication.
